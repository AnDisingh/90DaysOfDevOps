### Part 2: Scenario-Based Practice

**Scenario 1: Service Not Starting** 

# 1. Check service status
systemctl status myapp
# Result: systemd is not running in this WSL environment.

# 2. Check service logs
journalctl -u myapp -n 50
# Result: No journal files were found.

# 3. Check whether service starts at boot
systemctl is-enabled myapp
# Result: not-found

# 4. Check failed services
systemctl --failed
# Result: systemd is not running in this WSL environment.

What each command tells--
systemctl status myapp
→ Shows whether myapp is active, inactive, or failed and often gives the immediate error.
journalctl -u myapp -n 50
→ Shows the last 50 log entries for myapp, helping identify the actual failure.
systemctl is-enabled myapp
→ Checks whether myapp is configured to start automatically after boot.
enabled → starts at boot
disabled → does not start automatically
systemctl --failed
→ Lists services that are currently in a failed state.

### Service Logs - SSH

I tried to inspect the SSH service using systemd:

systemctl status ssh
journalctl -u ssh -n 50
journalctl -u ssh -f

The commands failed because my Ubuntu WSL environment is not
running systemd as PID 1.

I confirmed this using:

ps -p 1 -o pid,comm,args

PID 1 is `/init`, not `systemd`.

Therefore, `systemctl` cannot manage services and `journalctl`
cannot access systemd journal logs in this environment.

**Scenario 4: File Permissions Issue**

Step 1: Go to the Linux Home Directory
# cd ~
Why did I use this command?

cd means change directory.

The ~ represents my user's home directory.

In my case:

/home/dipesh

I moved to my Linux home directory because I wanted to practice Linux file permissions on a normal Linux filesystem instead of the Windows-mounted /mnt/c filesystem.

Step 2: Create the Script File
# touch backup.sh
Why did I use this command?

touch creates a new empty file if the file does not already exist.

I used it to create the script that I wanted to test.
The file was:

backup.sh

Step 3: Check the File Permissions
# ls -l backup.sh
Output
-rw-r--r-- 1 dipesh dipesh 0 Aug 19 14:10 backup.sh
Why did I use this command?

ls lists files.

The -l option means long format, which displays detailed information including:

File permissions
Owner
Group
File size
Date/time
File name

The important part was:

-rw-r--r--

There was no x permission.

In Linux:

r = read
w = write
x = execute

Therefore, the script did not have execute permission.

Step 4: Try to Execute the Script
# ./backup.sh
Output
bash: ./backup.sh: Permission denied
Why did I use this command?

./ means execute the file from the current directory.

I used:

./backup.sh

to test whether the script could be executed.

The Permission denied error confirmed that the file did not have execute permission.

Step 5: Add Execute Permission
# chmod +x backup.sh
Why did I use this command?

chmod means change mode.

It is used to change file permissions.

The +x means:

+ = add
x = execute permission

Therefore:

chmod +x backup.sh

adds execute permission to the script.

Step 6: Verify the New Permissions
# ls -l backup.sh
Output
-rwxr-xr-x 1 dipesh dipesh 56 Aug 19 14:14 backup.sh
Why did I use this command?

I used ls -l again to verify that the execute permission was successfully added.

Before:

-rw-r--r--

After:

-rwxr-xr-x

The x permission is now present.

Step 7: Execute the Script Again
# ./backup.sh
Output
Backup script executed successfully!
Why did I use this command?

I ran the script again to verify that the permission problem had been fixed.

The script executed successfully, which confirmed that adding execute permission solved the problem.
